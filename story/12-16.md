# Phase 3 チケット

## [Story 12] シードノード（ヘッドレスピア）

### ユーザーストーリー

nch ネットワークの安定性のために、長時間稼働するヘッドレスノードが過去の投稿を保持し、新規参加者がデータを取得できる。

### 受け入れ条件

- [ ] Node.js でブラウザなしに動作する
- [ ] core（domain, usecase, controller）をブラウザ版と共有する
- [ ] IPeerConnectionFactory の Node.js 実装（node-datachannel 等）
- [ ] IndexedDB の代わりにファイル or SQLite で永続化
- [ ] シグナリングサーバーに接続してピアと WebRTC 接続を確立する
- [ ] gossip で投稿を受信・保存・再ファンアウトする
- [ ] 他のピアと対等。管理権限や特権はない
- [ ] シグナリングサーバーと同居可能

### 設計メモ

- Adapter 層のみ差し替え。UseCase / Domain は変更なし
- IPeerConnection / IDataChannel インターフェースが Story 7 で定義済み
- IPostStore の永続化実装を差し替える（IndexedDBPostStore → FilePostStore or SQLitePostStore）

## [Story 14] ロード表示

### ユーザーストーリー

掲示板を開いたユーザーとして、接続中や過去ログ読み込み中の状態がわかる。

### 受け入れ条件

- [ ] シグナリングサーバーへの接続中に「ネットワークに接続中...」が表示される
- [ ] state 受信待ちの間に「過去ログを取得中...」が表示される
- [ ] state 受信完了 + 投稿フォーム有効化で通常表示に切り替わる
- [ ] ピアが 0 の状態で「他のユーザーを待っています」が表示される
- [ ] シグナリングにも繋がらない + ピア 0 で「ネットワークに接続できません」が表示される
- [ ] 操作をブロックしない。ステータス表示のみ

## [Story 15] 板・スレ対応

### ユーザーストーリー

掲示板のユーザーとして、複数のスレを閲覧でき、新しいスレを立てられる。

### 受け入れ条件

- [ ] 板一覧は constants に定数定義（増やすにはデプロイが必要）
- [ ] スレ一覧が表示される（state 交換から取得）
- [ ] スレを選択して開ける
- [ ] 新規スレ作成が可能
- [ ] スレ作成は gossip で即座に全ノードに伝播する
- [ ] 新規参加ノードが既存スレを state 交換で発見できる
- [ ] 1板あたり最大 100 スレ（MVP 後に dat 落ちを実装）
- [ ] 1スレあたり最大 1000 レス

### 設計判断

```typescript
// GossipMessage に追加
type GossipMessage =
  | { type: "post"; post: Post; ttl: number; path: string[] }
  | { type: "thread_created"; thread: ThreadMeta; ttl: number; path: string[] }

type ThreadMeta = {
  threadId: string;
  boardId: string;
  title: string;
  createdAt: number;
};
```

- 新規スレ作成: gossip で即座に伝播（6秒で全ノード到達）
- 既存スレの発見: state 交換で同期（最悪 23 秒で収束）
- ジェネシススレを constants にハードコード（空表示防止）

## [Story 16] gossip ピア発見 + CYCLON シャッフル

### ユーザーストーリー

シグナリングサーバーに依存せず、ピア同士で新しい接続先を発見できる。

### 受け入れ条件

- [ ] CYCLON シャッフルで passive view（最大 30 ピア）を構築する
- [ ] 定期的（30秒ごと）にランダムなピアとピアリストのサブセットを交換する
- [ ] active view のピアが dead になったら passive から昇格する
- [ ] DataChannel 経由のシグナリング中継が動作する（GossipMessage type: "signaling"）
- [ ] シグナリングサーバーなしで新規 WebRTC 接続を確立できる

### 設計判断

```typescript
type GossipMessage =
  | { type: "post"; ... }
  | { type: "thread_created"; ... }
  | { type: "signaling"; envelope: SignalingEnvelope; ttl: number; path: string[] }

type DataChannelMessage =
  | { type: "gossip"; message: GossipMessage }
  | { type: "heartbeat" }
  | { type: "state"; threads: StateEntry[] }
  | { type: "sync"; posts: Post[] }
  | { type: "shuffle"; peers: string[] }
```

- shuffle は TTL 1（直接ピアのみ）。gossip に乗せない
- passive view の lastSeen は gossip の path に含まれるピア ID で更新する
- passive からの昇格時は lastSeen が新しい順に接続を試みる
