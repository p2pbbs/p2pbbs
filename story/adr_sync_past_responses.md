# ADR: P2P データ同期戦略

## ステータス

承認済み（2026-04-30）

## コンテキスト

### nch のネットワーク構造

nch は WebRTC DataChannel ベースの P2P 掲示板。各ノード（ブラウザタブ）は最大 8 本の DataChannel を保持し（MAX_ACTIVE_PEERS = 8）、ランダムに選ばれたピアと接続する。シグナリングサーバーは SDP/ICE の中継のみを行い、投稿データやメタデータは一切保持しない。

シグナリングサーバーは複数の運営者が独立して立てることを想定しており、特定のサーバーが「正本」となることを許容しない。全てのデータの伝播は P2P の gossip と state 交換で行う。

### 新規投稿の伝播（既に実装済み）

新規投稿は gossip プロトコルで伝播する。投稿者が GossipMessage（type: "post"）をファンアウト 8 で直接ピアに送信し、受信したノードが TTL をデクリメントして再ファンアウトする。ランダムグラフの理論により、100,000 ノードのネットワークでもファンアウト 8、TTL 7 で全ノードに到達する。

### 解決すべき3つの問題

**問題1: 過去の投稿を受け取れない。** gossip は「新規投稿が発生した瞬間」にのみ伝播する。あるスレに既に 50 レスが存在する状態で新規ノードが参加しても、その 50 レスは gossip では届かない。新規ノードから見るとスレが空に見える。

**問題2: スレ一覧を知る手段がない。** 同様に、既に存在するスレの一覧も gossip では伝播しない。新規ノードから見ると板にスレが1つもない状態になる。

**問題3: 新規ノードの LamportClock が 0 から始まる。** nch ではスレ内の投稿順序を Lamport clock で決定する。各ノードが持つ LamportClock は「受信した投稿の最大 lamport 値」で更新される（clock.merge）。新規参加ノードは過去の投稿を受信していないため LamportClock = 0 から始まる。この状態で投稿すると lamport = 1 となり、本来は51番目の投稿であるにもかかわらずスレの先頭付近に表示されてしまう。

## 検討した選択肢

### 選択肢A: Pull 型（request/response）

新規ノードが直接ピアまたはネットワーク全体に「このスレのデータをくれ」と要求する方式。

**A-1: 直接ピアのみに聞く（hop 1）**

新規ノードが直接繋がっている 8 ピアに sync_request を送り、持っているデータを返してもらう。

問題: 直接ピアがデータを持っていない可能性が高い。例えば 5ch に投下された直後、5 ノード（長時間稼働）が 50 レスを保持している状態に 1000 ノードが一斉参加するケースを考える。シグナリングサーバーはランダムに 3 件のピアを紹介するため、新規ノードの直接ピア 8 本のうち少なくとも 1 本がデータ保持ノード（5/1005）に当たる確率は：

```
1 - (1000/1005 × 999/1004 × 998/1003 × 997/1002 × 996/1001 × 995/1000 × 994/999 × 993/998)
≈ 1 - 0.961
≈ 3.9%
```

つまり 96% の新規ノードは直接ピアにデータ保持ノードが1つも含まれない。データの完全復元が保証されない。

**A-2: gossip で request を撒く**

sync_request を TTL 付きの gossip で全ノードに撒き、データを持っているノードが応答する方式。

問題: 応答の通信量が爆発する。100 レスのスレで 20 ノードがデータを保持していた場合、20 ノードが各 100 投稿を re-gossip する。1 Post ≈ 500 bytes として：

```
応答メッセージ数: 20 ノード × 100 投稿 = 2,000 メッセージ
各メッセージの伝播: ファンアウト 8 × 最大 7 ホップ → 100,000 ノードに到達
総転送量: 2,000 × 100,000 ≈ 200,000,000 メッセージ転送
（seen Set で重複排除されるが、20 ノードが同時に送り始めるため初期の重複が激しい）
```

**A-3: 多段 relay（hop 2-3）**

sync_request に「応答先ピア ID（replyTo）」を含め、中間ノードが応答を要求元に中継する方式。hop 2 で 8 × 8 = 64 ノードに到達する。

問題: 応答のルーティング（replyTo の中継）の実装が複雑。DataChannel 経由シグナリング（宛先指定のメッセージ中継）と本質的に同じ仕組みが必要になる。

### 選択肢B: シグナリングサーバーにメタデータを持たせる

join 時にピアが自分の maxLamport を送り、シグナリングサーバーが集約して discover の応答に含める。

**却下理由:** nch のシグナリングサーバーは複数の運営者が独立して立てることを想定している。あるサーバーに繋いだノード群と別のサーバーに繋いだノード群が同じ P2P ネットワーク上にいた場合、サーバー間で保持するメタデータが異なり「どの状態が正か」の問題が起こる。シグナリングサーバーにデータの正本性を持たせることは P2P の思想に反する。

### 選択肢C: Anti-entropy（定期的なランダムピアとの同期）

定期的（例: 30 秒ごと）にランダムなピアと「持っているもの」を比較して差分を送り合う。gossip protocol の理論で知られた手法。

**却下理由:** 全ノードのデータが収束するまでに O(N log N) ラウンドかかる。N = 100,000、ラウンド間隔 30 秒の場合：

```
100,000 × log(100,000) × 30秒 ≈ 100,000 × 17 × 30 ≈ 51,000,000 秒
```

実用的な時間で収束しない。（注: anti-entropy の「ラウンド」は各ノードが独立にランダムなピアを選んで同期する1回の試行を指す。）

## 決定

**Push 型の state 交換 + 差分 sync** を採用する。

### 基本原理: 水の流れモデル

要求起点（pull）ではなく、データを持っている側が自発的に配る（push）。各ノードが直接ピアとスレのメタデータ（maxLamport）を定期的に交換し、相手より自分が進んでいるスレを検知したら差分の Post を push する。水が高いところから低いところへ流れるように、lamport が大きいノードから小さいノードへデータが伝播する。

ネットワーク全体でこれを全ノードが行うため、データは段階的にホップを重ねて全ノードに行き渡る。特定のノードを「探す」必要がなく、ルーティングの問題を回避する。

### 2種類のメッセージ

**state（メタデータ交換）:** 各スレの threadId, maxLamport, postCount を含む軽量データ。直接ピアとの 1 対 1 通信。gossip に乗せない。

**sync（実データ送信）:** 差分の Post オブジェクトの配列。state 交換で「相手が遅れている」と判明したスレについて、相手が持っていない Post を push する。

この2つを分離する理由: state は数 KB と軽いため即座に届く。新規ノードは state を受け取った時点で各スレの maxLamport を知り、LamportClock を正しい値に更新できる（問題3の解決）。sync は数百 KB と重いが、後から届いても表示が徐々に埋まるだけで問題ない。

### データ構造

```typescript
type DataChannelMessage =
  | { type: "gossip"; message: GossipMessage }
  | { type: "heartbeat" }
  | { type: "state"; threads: StateEntry[] }
  | { type: "sync"; posts: Post[] }

type StateEntry = {
  threadId: string;
  maxLamport: number;
  postCount: number;
};

// GossipMessage に追加（新規スレ作成の即時伝播用）
type GossipMessage =
  | { type: "post"; post: Post; ttl: number; path: string[] }
  | { type: "thread_created"; thread: ThreadMeta; ttl: number; path: string[] }
```

state と sync は DataChannelMessage として DataChannel 上で直接送受信する。gossip には乗せない。heartbeat と同じレベルの 1 対 1 通信。

### state 交換のタイミング

**即時交換:** DataChannel が open したタイミングで、双方がフル state（全スレの StateEntry）を送信する。新規ノードが参加した直後に直接ピアから即座にスレ一覧と maxLamport を取得できる。

**定期交換（10 秒間隔）:** 直接ピアに差分 state を送信する。「差分」はピアごとに「前回そのピアに送った state」を記録し、変化があったスレの StateEntry のみを送信する。

```typescript
// ピアごとに前回送信した各スレの maxLamport を記録
private readonly lastSentState = new Map<string, Map<string, number>>();
```

- 新規ピア（lastSentState にエントリなし）→ フル state 送信
- 既存ピア → 前回との差分のみ送信
- ピア離脱 → 記録を削除
- CYCLON シャッフルでピアが入れ替わった場合 → 新規ピアとしてフル state 交換

### 穴の検知

あるノードが lamport 1-2 を持たずに lamport 3-8 だけを持つケースがありうる（途中参加で gossip が部分的に到達しなかった場合など）。maxLamport だけでは穴を検知できない。

StateEntry に postCount を含めることで「maxLamport = 8 だが postCount = 6（本来 8 件あるべき）」を検知できる。穴がある場合は postIds リストを交換して具体的な差分を特定する。

### 新規スレ作成の伝播

新規スレの作成は gossip で即座に全ノードに伝播する（GossipMessage type: "thread_created"）。ファンアウト 8、TTL 7 でランダムグラフの直径 6 ホップ以内に全ノードに到達する。約 6 秒。

既存スレの発見は state 交換で行う（即時交換 + 定期交換）。

### 投稿フォームの有効化タイミング

新規ノードの参加フロー:

```
1. シグナリングサーバーに接続し、ピアリストを取得する
2. 各ピアと WebRTC DataChannel を確立する
3. DataChannel open 時に即時 state 交換が実行される
4. 全直接ピアから state を受信した時点で、受信した maxLamport の最大値で LamportClock.merge を実行する
5. 投稿フォームを有効化する
6. バックグラウンドで sync（実データ）が到着し、過去の投稿が徐々に表示される
```

全直接ピアの maxLamport が 0 だった場合（全ピアが新規参加ノードの場合）はそのまま投稿を許可する。直接ピアよりも先のホップにデータ保持ノードがいる可能性はあるが、それを待つと数十秒の遅延が生じ UX が悪化する。P2P の eventual consistency として許容する。

## 見積もり

### 前提パラメータ

| パラメータ | 値 | 根拠 |
|-----------|-----|------|
| MAX_ACTIVE_PEERS | 8 | チャーン耐性とバックグラウンド通信量のバランス |
| スレ数上限 | 100/板 | 5ch 準拠 |
| レス数上限 | 1,000/スレ | 5ch 準拠 |
| 1 Post のサイズ | ~500 bytes | name + body + id + signature + publicKey + boardId + threadId + lamport 等 |
| 1 StateEntry のサイズ | ~50 bytes | threadId(36B) + maxLamport(8B) + postCount(4B) |
| state 定期送信間隔 | 10 秒 | |
| heartbeat 送信間隔 | 30 秒 | |
| ランダムグラフの直径 | ~6 ホップ | log₈(100,000) ≈ 5.5 |

### 24 時間通信量

前提: 8 ピア接続、100 スレ、1 日あたり 1,000 投稿

**heartbeat:**

```
送信: 30 秒ごと × 8 ピア × ~20 bytes = 5.3 bytes/秒
受信: 同量
24h: 5.3 × 2 × 86,400 ≈ 0.9 MB
```

**state（差分、10 秒間隔）:**

差分 state は「前回そのピアに送ってから変化したスレ」のみ送信する。アクティブなスレ（10 秒間に投稿があったスレ）が平均 5 個と仮定:

```
差分: 10 秒ごと × 7 ピア（既存） × 5 スレ × 50 bytes = 175 bytes/秒
フル: CYCLON シャッフルで 30 秒に 1 本入れ替わり × 100 スレ × 50 bytes = 167 bytes/秒
合計: ~340 bytes/秒
24h: 340 × 2 × 86,400 ≈ 59 MB
```

**gossip（新規投稿）:**

```
受信: 1,000 投稿/日 × 500 bytes = 500 KB
送信（再ファンアウト）: 1,000 × 500 bytes × 8 ピア = 4 MB
24h: ≈ 5 MB
```

**sync（差分 push、ピア入れ替わり時）:**

```
CYCLON シャッフルで 30 秒に 1 本入れ替わり → 1 日に ~2,880 回
各回の差分: 10 秒分の新規投稿 ≈ ~0.1 投稿 × 500 bytes = 50 bytes
24h: 2,880 × 50 × 2 ≈ 0.3 MB
（新規参加時のフル sync は別途: 最大 1,000 レス × 500 bytes = 500 KB × 数回）
```

**合計: 約 65 MB/日**

モバイル回線（月間 3-20 GB プラン）で24 時間繋ぎっぱなしにした場合、月間約 2 GB。通信量が制限されたプランでは注意が必要だが、許容範囲。

### 収束速度

state 伝播はホップごとに「直接ピアに state を送信 → 差分を検知 → sync で push」が連鎖的に発生する。

```
収束時間 = ホップ数 × 1ホップあたりの遅延（state 送信間隔 + sync 転送時間）
```

| シナリオ | 収束時間 | 計算 |
|---------|---------|------|
| 直接ピアがデータを持っている | 2-3 秒 | 即時 state 交換 + sync 転送 |
| 2 ホップ先にデータ保持ノードあり | 10-13 秒 | 即時交換 → 1 ホップ先が定期 state (10s) で伝播 |
| 最悪（6 ホップ先のみ） | 60 秒 | 6 × 10 秒 |

### 大量参加シミュレーション

5ch にスレ URL が投下された直後を想定する。

**前提:**

- 既存ノード: 5（長時間稼働、50 レス保持）
- 新規ノード: 1,000（一斉参加）
- MAX_ACTIVE_PEERS = 8
- シグナリングサーバーはランダムに最大 3 件のピアを紹介

**新規ノードの直接ピアにデータ保持ノードが含まれない確率:**

全ピア数 1,005 のうちデータ保持ノードは 5。新規ノードが 8 ピアを選んで 1 つもデータ保持ノードに当たらない確率:

```
P(0本) = C(1000,8) / C(1005,8) = (1000/1005)(999/1004)(998/1003)...(993/998) ≈ 0.961
```

約 96% の新規ノードが直接ピアにデータ保持ノードを持たない。

**しかし state 伝播の連鎖で解消される:**

```
t=0s:   5 ノードがデータ保持
t=3s:   5 × 8 = 40 ノードが即時 state 交換でデータ取得（データ保持ノードの直接ピア）
t=13s:  40 × 7 ≈ 280 ノードが定期 state (10s) で取得（2 ホップ目）
t=23s:  280 × 7 → ほぼ全ノードに到達（3 ホップ目）
```

約 23 秒で全ノードがスレ一覧と maxLamport を取得できる。

### LamportClock ズレの影響

新規参加ノードが直接ピアから受け取った maxLamport がネットワーク全体の最大値よりも小さい場合、そのノードの投稿の lamport 値が「本来あるべき値」よりも小さくなり、表示順序がズレる。

ズレの最大幅は「gossip の伝播遅延中にネットワーク全体で行われた投稿数」に等しい。gossip はファンアウト 8、TTL 7 で直径 6 のランダムグラフを約 6 秒で伝播する。

| ネットワーク全体の投稿レート | 6 秒間のズレ（投稿数） |
|---------------------------|---------------------|
| 0.1 投稿/秒（MVP 想定） | 0-1 |
| 1 投稿/秒 | 6 |
| 10 投稿/秒（超アクティブ） | 60 |

なお、大量参加時には多くの新規ノードが同じ「state 未受信」状態にあるため、これらのノードの lamport 値は互いに近い値域に集中する。相対的な順序は保たれやすく、掲示板の UX としてはほぼ気づかない。

## エッジケース

| ケース | 挙動 | 許容 |
|--------|------|------|
| 直接ピア 8 本が全員新規参加ノード | スレ一覧が空に見える。定期 state 伝播で 10-23 秒後に解消 | ○（ローディング表示で対応） |
| sync 中に新規投稿が gossip で到着 | sync の Post と gossip の Post が混在するが、post.id（コンテンツハッシュ）で重複排除される | ○ |
| ネットワーク分断 | 分断された側のデータは届かない。分断回復後に state 交換で同期される | ○（不可避） |
| 全ノードがデータを喪失（全員がタブを閉じた） | データ復元不可能 | ○（P2P の本質的制約） |
| 大規模スレ（1,000 レス）の sync | 差分 push で 500 KB。DataChannel の 1 対 1 通信なので帯域は問題なし | ○ |
| 1,000 スレ環境での state | フル state が 50 KB/回。やや重い | △（差分 state で軽減） |
| 悪意あるノードが maxLamport を詐称 | sync で偽の Post を返しても Ed25519 署名 + SHA-256 ハッシュ検証で弾かれる。maxLamport 詐称は「sync を求められるが返せない」だけで実害は小さい | ○ |
| ノードが部分的にデータを持つ（lamport 1-2 がなく 3-8 だけ保持） | maxLamport = 8 だが postCount = 6 で穴を検知。postIds 交換で差分を特定して補完 | ○ |

## スレ一覧の空表示対策

新規参加直後にスレ一覧が空に見える問題への対策:

| 対策 | 説明 |
|------|------|
| ローディング表示 | 「スレ一覧を取得中...」を表示。最大 23 秒で解消 |
| ジェネシススレ | MVP で 1 スレを constants にハードコード。state 受信前でも最低 1 スレは見える |
| 新規スレは gossip | 作成時に gossip で即座に伝播する。state 交換を待たずに約 6 秒で全ノードに到達 |

## 前提・制約

- スレは最大 1,000 レス（5ch 準拠）
- 板は最大 100 スレ。古いスレの dat 落ちは MVP 後に実装
- 板一覧は constants に定数定義。gossip や state 交換は不要
- シグナリングサーバーは SDP/ICE の中継のみ。メタデータを保持しない
- シードノード（Node.js ヘッドレスピア）は他のピアと対等であり、管理権限や特権を持たない。長時間稼働の「結果」としてデータを多く保持するだけであり、「シードノードが存在する」ことを前提とした設計にしない
